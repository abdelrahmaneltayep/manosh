# Feature 16 — Multi-Currency & Multi-Language (GCC-First)

Sell across borders: buyers see the portal in their language (Arabic RTL first,
then EN/FR) and prices in their currency. Dark-launched behind `MANNON_FF_I18N`;
when off, everyone gets the store default locale + currency exactly as before.

## RTL — mirror the shell, not just the text

The portal shell (`portal.tsx`) reads the session locale cookie and sets
`dir`/`lang` on the `<main>` container. For Arabic `dir="rtl"` **mirrors the whole
layout** (`portal.css` RTL rules flip inline flows, alignment, and inputs), while
prices/quantities stay LTR so numbers read correctly. `localeDir()` (pure) is the
single source of truth for direction.

## Locale + currency resolution

`resolveBuyerContext(shopDomain, { companyId, memberId, cookieLocale })`:

- **Locale**: session cookie (if supported + enabled) > member preference >
  company preference > store default.
- **Currency**: member > company > store default; only **enabled** currencies
  (store currency + `supportedCurrencies`) are honored.

Preferences persist in `LocalePreference` (member- or company-level). Changing the
language (`/portal/locale`) sets the cookie **and**, for a signed-in buyer, the
member preference (which also localizes their emails). Event `LOCALE_CHANGED`.

## Money — we never settle it

Guardrail #1 holds: Shopify settles money. Currency handling here is **presentation
of an agreed price** plus rate-locking:

- **`resolveDisplayPrice`** (pure): a merchant **per-currency contract override**
  (exact price, no FX) > **conversion** at the known rate > the **base price** in
  the store currency (clean fallback when no rate).
- **`convertAmount`** is cents-safe (no floats).
- **`assertSingleCurrency`** enforces one currency per quote/order.

## Rate-locking (the guarantee)

On submit, `resolveLockedFx` → pure `lockFx` sets `Quote.displayCurrency` +
`Quote.displayRate` from the store base → the buyer's currency at that moment. A
later FX change **cannot** alter an issued quote or its counter-offer; invoices
show the locked rate. No rate available → the quote stays in the store currency at
rate 1.

## Localized emails

`resolveTemplate(key, overrides, locale)` layers **shop override > locale
translation > EN default**, so every email always resolves. Arabic translations
ship for the core buyer templates (invoice, reminders, pay-link, follow-up, member
invite, tax-verified); everything else falls back to EN. A regression test asserts
every template × locale resolves to a non-empty subject + body.

## Data model (migration `f16_multi_currency_language`)

- `CurrencyRate { base, quote, rate, source }` — Shopify or manual, unique per (shop, base, quote).
- `LocalePreference { companyId?, memberId?, locale, currency }`.
- `PriceListCurrencyOverride { entryId, currency, price }` — per-currency contract price on an F3 entry.
- `Shop.defaultLocale / supportedLocales / supportedCurrencies / i18nStrings`; `Quote.displayCurrency / displayRate`.
- Event `LOCALE_CHANGED`.

## Reconciliation / notes

- **Store base currency** is read from the live catalog (`getStoreCurrency`,
  cached), not a new column.
- Live **Shopify Markets** rate sync is a documented follow-up; today rates are
  merchant-set (`source=MANUAL`) or seeded as `SHOPIFY`.
- The portal shell offers all supported locales in the switcher (a display
  preference); currency/price resolution still respects the merchant's enabled set.
- No new Shopify OAuth scope. Full string translation of every portal route is
  incremental — the shell chrome + key flows are localized; `t()` + the dictionary
  make adding strings mechanical.
